# 0002 只认平台盖过章的文件引用

- 状态：已决定
- 日期：2026-10-29

## 背景

用户 `@` 引用文件时，日志里存两份：

- `<user_references>`（在 `system-reminder data-role="additional-data"` 里）：
  `"D:\\code\\...\\scripts\\fork.py"` —— 完整绝对路径，平台写的
- `<user_query>` 体内：`@"scripts\\fork.py"` —— 相对路径或绝对路径，紧挨着用户的话

而 `@file:"…"` 这个形式，全库 2149 条用户发言里出现 **0 次**。之前为它写的正则和用例，是照着「应该存在」的推断做的，一次都没触发过——由用户随手发一个文件引用才照出来。

## 决定

体内 `@"…"` 只有在**同一条消息的 `<user_references>` 里列过这个路径**时，才换成
`[文件 src/fork.py]`；对不上的一律原样留着。

## 理由

- `@"…"` 和 C# 的 verbatim string 语法完全相同。全库 28 条含 `@"…"` 的消息里，7 条是代码片段（`@"..."` 占位、`") and x != "` 之类）。
- 平台在 `<user_references>` 里的列举，是「这条确实是文件引用」的唯一可靠信号。猜语义会改坏代码，而那正是这个仓库一直在防的损失形态。
- 另一个选择是干脆不动 `@"…"`。但那样相对路径虽然还在，读者要自己意识到那是文件引用——而包是给下一个 agent 读的，它没有这层上下文。

## 后果

- 实测：全库 21 处换成占位，11 处原样留着。那 11 处是有意的，不是漏了。
- `@file:"…"` 的正则和用例保留。它是死分支，但删掉要动三条用例、换不来任何收益。
- `<user_references>` 块本身照旧整块删：相对路径已经在体内了，留着只是重复噪音。
- 日志里的路径是**双反斜杠**，比对前要归一（`norm_ref`），否则 `[文件 scripts\\fork.py]` 看着像故障。
