# 0004 代码里的标签不算结构

- 状态：已决定（**部分取代 [0001](0001-标记在代码块里照常渲染.md) 的 `@image` 分支**）
- 日期：2026-10-29

> 0001 选 B「代码块里也照常渲染」，那是为 `@long-text` / `@file` / `@skill` 定的——它们的占位
> 只是把标记换成一句人话，不产生新事实。`@image` 不同：`[图片 ×.png]` 会被读成一条附件事实，
> 而原位置只剩空反引号。所以 image 这一支从这里起按位置判，其余三样仍按 0001 渲染。

## 背景

`<user_query>` 和 `@image#N:name` 都被当成结构标记来切分内容。但这两个字符串
会以**字面文本**的形式出现在正文里——用户在讨论这个工具本身时，必然要写它们：

- `AGENTS.md` 里就有一整条纪律：`` `<user_query>` 体内是用户原话 ``
- `README.md` 里写着 `` @image#1:a.png，这样改对不对 ``
- 而 `AGENTS.md` 会被整篇注进 `user-context` 信封

于是切分从错误的位置开始。这不是理论风险，实测已经发生：

| 会话 | 症状 |
|---|---|
| `94523526`（本会话） | 第 13 条发言变成 AGENTS.md 片段，开头凭空多一个 `[图片 a.png]` |
| `94523526`（第 1 条） | 同一条消息里，注入被当原话、原话被当注入，凭空多一个 `[图片 a.png]` |
| `90e337fc` | 13383 字符进去，输出成了 AGENTS.md 的片段 |
| `de650383` | 9459 → 2456，丢了 74% 的原话 |

最坏的形态是**凭空造数据**：`[图片 a.png]` 挂在一句根本没贴图的话开头。
退出码 0、照常打印「已导出」——正是这个仓库一直在修的那类。

## 决定

**被反引号包住的标签不算结构。**

1. `QUERY_RE` 两头都加了判据：`(?<![`])<user_query>…</user_query>(?![`])`。
   只判一头不够——非贪婪会从真开标签一路吃到反引号里的假闭合。
2. `AT_IMAGE_RE` 加了 `(?<![`])`；`render_marks` 里 image 分支也按位置判：
   前面是反引号就原样留着，否则当附件删掉、由 `[图片 …]` 补回来。
3. 注入信封（`system-reminder data-role="…"`）**必须在切分之前剥掉**。
   否则 AGENTS.md 里那个字面标签会先被正则认走。

## 理由

- 判据是位置的，不是语义的。和 `@long-text`「看这个标记后面跟没跟引文块」
  是同一条纪律：**位置比语义可靠**。
- 试过但不行：拿 `<image_local_path>` 在不在当判据。平台偶尔漏记路径
  （`9f06e10b` 那条：用户确实贴了 `Clipboard_Screenshot.png`，日志里没有 path），
  按路径判会把**真附件**当成正文讨论，把 `@image#1:xxx.png` 原样丢给新对话。
- 反方案（认行内代码的完整边界、处理未闭合反引号）已经在 ADR-0001 里否过：
  未闭合的反引号会把后面正文整段划进「代码区」，为边缘场景引入新的误判面。

## 后果

- 全库 241 个会话逐条对比：**误伤 0 条、凭空多出 0 条**，内容变化的正好是上面
  那 5 条。91 条真带图消息里，`@image` 残留 0 条。
- 代价：讨论用的标记如果**没**写进反引号（裸的 `@image#1:a.png，这样改对不对`），
  仍会被当成附件，渲染成 `[图片 a.png]`。信息保住了，只是原话被改写——
  比删掉原文、再造一张假图要好。
- 同一族还剩一处没修，已记进工作区日志：`de650383` 有 423 字符的裸注入
  （`**必须剥的注入**：…`）直接躺在 `<user_query>` 外面，**不在任何标签里**，
  所以按标签剥的规则碰不到它。它会作为「体外残留」拼在导出末尾。
  这是「多出噪音」，不是「丢数据」，单独一轮处理。
