# 0008 原文全留,不重放 surface

- 状态:已决定
- 日期:2026-10-31

## 背景

dsh 上下文满时会自动压缩。日志不是简单追加,而是记录**改写操作**:

```
{"seq":1264,"type":"user/message","surfaceOp":{"op":"replace","startSeq":8,"endSeq":651},
 "sourceEventSeqs":[1261,1263,8,9,10,…],
 "data":{"source":{"kind":"compact-checkpoint"},"content":[{"type":"text","text":"## Primary Request and Intent…"}]}}
```

即:第 1264 条事件用一份 9164 字的摘要**替换**了第 8~651 条对模型可见的
全部内容。原始事件仍在日志里,一条没删。

所以同一段历史在文件里有两种读法:

1. 按文件顺序读全部事件 → 拿到完整原始对话 + 一份摘要;
2. 重放 `surfaceOp` → 拿到模型此刻真正「看得见」的对话。

## 决定

读文件里的全部原始事件。**不重放 `surfaceOp`**。压缩检查点消息本身不导出,
只在 header 记一处「压缩 N 处(原文完整保留)」。

## 理由

- 检查点是原文的机器摘要,信息量严格小于原文。这个工具的用途是把背景搬到新
  对话,原文越多越好;留着摘要等于同一段内容出两份,还短的那份在前。
- 重放要正确实现 surface 语义(append / replace,以及 `startSeq`/`endSeq` 的
  边界、重叠、之后的追加)。手头只有 24 + 74 个 `replace` 样本,其中 98% 是
  同一条 system prompt 的换位;真正重要的只有 3 处压缩。用 3 个样本去猜一套
  改写语义,猜错的后果是静默少一段历史——比不实现更糟。
- 日志是 append-only 的,不重放不会丢东西;重放才可能丢。

## 后果

- 导出内容包含模型「已经忘了」的段落。这是有意的:新对话没有上下文窗口压力,
  拿全量比拿摘要划算。`--compact` / `--from` 负责控制体积。
- header 会写「压缩 1 处」。它只是让人知道模型上下文曾经断过一次,不是内容
  缺口——原文都在。
- 已知风险:dsh 如果以后把「改写」用于压缩以外的目的(例如撤回一条消息),
  不重放就会把撤回的内容当成正常发言导出去。届时 `surfaceOp` 的 `op` 里会
  出现新值,`corpus_check` 数不到这件事,只能靠人看一眼新样本。
