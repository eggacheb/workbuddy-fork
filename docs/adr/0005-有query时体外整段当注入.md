# 0005 有 `<user_query>` 时,体外整段当注入

- 状态:已决定(**收掉 [0004](0004-代码里的标签不算结构.md) 末尾留的那一处**)
- 日期:2026-10-29

## 背景

`de650383` 第 1 条发言:闭合的 `</user_query>` 后面跟着 420 字的
`**必须剥的注入**:…`(列着该剥哪些标签的那段说明),**不在任何标签里**。
`clean_outer` 是「按已知标签剥」的,碰不到它,于是它被当成「体外残留」
拼在导出末尾。导出照常、退出码 0、没人看得出来。

## 决定

`clean_user` 里,只要这条消息切出了 `<user_query>`,**体外剩下的文字一律不进导出**。
附件照旧从体外收——`<image_local_path>` 和图片名本来就在体外的部分。

反过来:**没有** query 的消息,体外那一段就是用户原话,一个字不动。

## 理由

- 先量再写。242 个会话、3185 条 user 消息(其中 2135 条带 query):
  体外残留非空的只有 **49 条**——47 条是 `clean_outer` 自己渲染出的重复 `[图片]`
  (附件另有 `[图片 名字](路径)` 一份记录),2 条是那段 420 字裸注入,
  **用户说的话 0 条**。
- 判据是位置的,不是「像不像注入」。按措辞认(给 `**必须剥的注入**` 单加一条
  `NOISE_RES`)能治这一条,但平台换一句就漏;那种规则还会永远留在代码里,
  没人记得它当初是为什么加的。这一条正是「没见过的那种注入」的样本。
- 另一个想当然的反方案:体外残留里有 `[图片]` 就丢、没有就留。两个方向都判错——
  那 47 条有 `[图片]` 但确实该丢,那 2 条注入没有 `[图片]` 却更该丢。

## 后果

- 全库逐条比对改动前后的 `clean_user` 输出:变化正好 49 条,**每一条都只是尾部
  少了那串残留,正文一字未动**(用 `新输出.startswith(旧输出)` 验的)。
  `corpus_check` 的四项指标一条没变:计入发言 2162、整条丢掉 1023、
  长引用占位 2、幽灵发言 0。
- 已知代价:如果平台以后把用户正文挪到 query 外面,它会被静默删掉——而体内
  照样有字,「计入发言」不会掉,看不出少了什么。所以光靠指标**不够**,
  补了一条机械判据:`corpus_check` 新增「体外残留」一项,数「有 query 且体外剥完
  还剩字(附件占位不算)」的消息条数,**变多就是回归**(`BAD_WHEN_UP`)。
  基线是 2(就是那两段 420 字);多出第 3 条,说明平台又塞了没认出来的东西——
  先回原文确认那不是人话。真出现了就改判据,**不要**加白名单:
  白名单是「这次见过的注入」的清单,和上面那条理由打架。
- 用例:`tests/test_clean.py` 的「有query时体外的残留」四条(注入被丢、没 query 的
  原话照留、体外重复的 `[图片]` 不会和附件记录撞成两份、残留指标的口径);
  `tests/test_corpus_check.py` 里的「体外残留」计数与两个方向的三条。
